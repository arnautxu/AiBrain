# R2 A1 runtime lifecycle — implementation and evidence

Scope: runtime service, workers and transport only. Baseline `bd898707ed590900a90bdd682ea3b39e97d32d25`. No UI, customer data, Melso execution, push or deployment.

## Source and mechanism map

Read-only Melso reference: `7c667dd1a41fee4bc2b5172649527cf9f4d26771`, `server/internal/daemon/daemon.go`, `server/pkg/agent/codex.go`, `server/internal/daemon/wsrpc.go`, `server/internal/daemon/processtree/{run,controller_unix,controller_windows}.go`, and `server/internal/daemon/execenv/isolation{,_unix}.go`. Full source inspection completed before implementation. David authorized copy/adaptation. This change adapts lifecycle invariants in TypeScript; it does not copy Go source, remove notices, embed credentials or execute Melso. The historical absence-of-license concern is not treated as a blocker to David's authorized adaptation.

- Melso claims remain owned through active-task registration and terminal cleanup; release/wakeup happens after cleanup. AiBrain registry owns each user runtime and must not release it while late startup can spawn.
- Melso context locking and generation fences reject stale registration/reconnection. AiBrain gateway currently awaits journal repair before spawning without a cancellation fence; managed stop drops its pointer while that await is pending. QA reproduced two orphan-process cases.
- Melso process-tree cleanup precedes retry; AiBrain R1 owned-process helper already enforces group ownership. Preserve it, including injected-factory direct-child semantics.
- Melso WS negotiation is generation-scoped and uncertain writes are not blindly replayed. Preserve AiBrain request ledger, scope-confirmed ACK and per-service audit roots.
- Melso daemon persistence does not mean a persistent model process: Codex backend starts an app-server per task. AiBrain deliberately reuses a per-user app-server and loaded threads. Do not claim either is inherently faster.

## Structural decisions and implemented path

| Source mechanism | AiBrain decision and connection |
| --- | --- |
| `daemon.go:308-336` cancellable context lock; registration/demotion generations | Gateway and managed runtime are terminal after stop. Post-journal and post-listen continuations check retirement. The service has per-user admission generations, including checks after user reads and before recovery retries. |
| `daemon.go:4872-4913` active ownership before claim release, cleanup before slot release | Stop retains resources until pending listen binds/fails and the owned child is gone. Registry startup timeout invokes this terminal stop before allowing a replacement. User stop invalidates then drains its admission before final registry stop. |
| `wsrpc.go:45-80,92-120` atomic cancel/write and per-connection generation | Deferred transport close wakes pending readiness; late configuration is refused. WebSocket connect captures its waiter; close during cursor/backlog I/O cannot revive connected state. Existing uncertain-request rejection and no model-action replay remain intact. |
| `codex.go:936` executeOnce and process-tree ownership | Retain R1 `owned-process.ts`, detached POSIX groups and injected-factory direct-child ownership. No broad PID/name killing, no change to another user's process. |
| `execenv/isolation.go:76-135` cancellable owned preparation helper | Adopt the post-await resource-creation fence, not a new preparation subprocess. AiBrain's journal repair is filesystem work; it may settle after cancellation but cannot subsequently spawn or bind. No additional model/runtime process is needed for this boundary. |
| Codex initialize/resume and daemon slots | Retain per-user persistent App Server, one coalesced initialization and concurrent thread routing. Existing warm-thread reuse skips unnecessary resume. Do not migrate wholesale to a per-task Go daemon without measured benefit and tenant/approval integration. |

The complete live path remains `workerAppServerForUser → registry.start → LocalGatewayWorkerRuntimeFactory → PrivateWorkerGateway → WebSocket transport → WorkerAppServerClient/router`. A rejected cleanup now propagates through registry close and configuration replacement; the previous registry remains reachable rather than publishing an overlapping replacement.

### Deterministic before/after

- QA's delayed journal tests were adapted into this worktree without modifying its artifacts. Both direct and managed-factory cases failed against the unmodified gateway baseline: one process was created after completed stop. Both now pass with zero late process creation and stopped health.
- Additional regressions cover delayed TCP listen (stop must wait), three concurrent starts/stops, pending deferred connect, real factory registry timeout then successful replacement, and stopping one user while the second remains healthy/alive.
- The service-level stop-during-initialize regression also failed before its fix: recovery returned a successful admission after stop. Per-user generation fencing now rejects both late successful initialization and late failed initialization, prevents automatic restart, and permits a later explicit new admission.
- Close during transport cursor loading or ready backlog cannot reopen it. Registry close failures remain visible and cleanup can be retried. Configuration replacement retains the old state after failure. Throwing diagnostic observers cannot leak a startup slot.

### Runtime phase telemetry

Production emits `codex.worker_lifecycle` with schema 1, installation/user scope, `phase`, `outcome`, `durationMs`. Phases are queue, provision, gateway_start and transport_connect, using monotonic time. The observer is non-authoritative and cannot fail startup. Existing `codex.app_server_request` adds initialize/account/resume/turn request-accepted and total durations; the B-owned HTTP/UI first-event trace remains untouched. No tokens, prompts, private paths or model responses are added to lifecycle logs.

## Real anonymous App Server check and limits

`src/runtime/workers/app-server-isolated.real.test.ts` uses the default production factory with an empty temporary HOME/CODEX_HOME/XDG tree. No auth was copied/read from the desktop, no prompts/turns were submitted, and no model was selected. Installed `/opt/homebrew/bin/codex` reports **0.152.1**, whereas the project-generated contract is **0.149.1**.

- First attempt: real initialize and account/read passed, account was null. Cumulative timings from startup: gateway 40.789ms, initialized 739.899ms, account 1273.457ms. Cleanup then failed closed with `kill EPERM` on the owned process-group liveness check. Do not count this attempt as passing acceptance.
- One bounded rerun with ownership-only diagnostics passed, alongside both existing real Node process-group tests. Cumulative timings n=1: gateway 20.887ms, initialized 531.543ms, account 879.010ms; unauthenticated. No cleanup-helper weakening was made. The first EPERM cause is unproven; no matching `app-server --stdio` process remained in a later read-only process check.
- `AIBRAIN_INSTALLATION_CONFIG`, `AIBRAIN_CODEX_AUTH_SCOPE`, `AIBRAIN_SHARED_CODEX_AUTH_SOURCE` and `CODEX_BIN` were unset (presence checked, no secret values read). No identified authenticated isolated test user/configuration was supplied. Provider cold/warm/three-chat inference is therefore deferred to the integrated candidate, not simulated as live performance.
- No Docker/Linux, Windows, browser, UI or deploy acceptance was performed. No Melso process/session or customer runtime was touched. ACK 5s / ENOTEMPTY flake remains separate and unexplained; it is not attributed to the startup race.
